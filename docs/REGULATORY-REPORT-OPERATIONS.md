## Receipt and review contracts

`POST /.netlify/functions/regulatory-report` accepts an explicit send-consent boolean, UUIDv4 request ID, country code, one of the eight current change types, title, public-change details, optional HTTP(S) source URL and optional effective date. It requires the same Origin and JSON. No account, name or email is requested. A submitted source URL is stored for a human, never fetched by the report handler. Details should contain public regulatory facts only, not employee, payroll or other personal records.

The modern Netlify handler uses platform `context.ip`, never request IP headers. Its documented contract is at [Netlify Functions API](https://docs.netlify.com/build/functions/api/#ip). Local Netlify context values are mocks; local tests do not prove production IP attribution. The server derives a daily HMAC key from trusted IP, UTC date and secret; it never stores raw IP in report tables.

One PostgreSQL transaction validates fields, serializes a request ID, checks its payload hash, locks a daily quota row, and saves receipt + unverified Gazette signal + pending review item + quota debit. An exact UUID/payload replay returns the original receipt even after the day or quota changes. Reusing that UUID with different payload returns conflict. At most five distinct accepted requests per daily key are allowed; a replay consumes no additional quota. Distinct requests for the same text count separately. Shared networks share a quota; address changes can obtain another quota. This is bounded abuse prevention, not a claim of person-level deduplication or bot elimination.

The receipt records original intake, not current review status. Only a validated database receipt produces browser success/reset. Header, body or database timeouts leave delivery unconfirmed and the form intact. Explicit retry reuses the same request ID; there is no automatic background retry. Starting a different report after an uncertain result may leave the earlier report received, and the UI explains that. Closing the page loses its in-memory draft and retry ID. No report content is sent to analytics or logged by the new endpoint.

Gazette records begin `verified=false`, `confidence=0`, `applied_to_tools=false`, with a clear community source label. Community admin approval/rejection uses the separate service-only `review_regulatory_report` RPC: it locks the receipt and atomically updates its exact Gazette and review rows. Repeated or opposite decisions stay consistent, including concurrent requests. Legacy scanner decisions keep their existing application path. Decisions do not award points or update calculator data. Legacy rejected-country reconciliation excludes community source rows (including future reports), while retaining nullable legacy source rows. The old 90-day scraper cleanup excludes the new non-null community report reason so retained receipt foreign keys cannot block unrelated cleanup. Admin text is escaped and source links are restricted to HTTP(S) without URL credentials.

Gazette's existing `change_type` CHECK has a narrower, underscore-based taxonomy. Intake preserves it: `minimum-wage` maps to `minimum_wage`, `paye-bands` to `paye_bracket`, and `pension-rate` to `pension_rate`. `social-security`, `new-levy`, `tax-threshold`, `cit-rate` and `filing-deadline` map to `other`; they are not recast as NHIF, VAT or tax relief. Every description starts with `[Reported UI type: <original>]` and the exact original type remains in `review_queue.metric`. Title/detail caps and the fixed type allowlist bound the full description to 2,177 characters / 8,597 UTF-8 bytes. No existing CHECK or legacy scanner taxonomy changes.

## Retention and operations limits

Quota keys become eligible for pruning 48 hours after their first accepted use. A later successful intake transaction removes at most 1000 expired keys using `SKIP LOCKED`. Idle sites, a backlog, or rolled-back/denied attempts can retain expired keys longer. There is no scheduled hard-delete job and no guaranteed deletion at the 48-hour mark. Operations must approve any stronger retention guarantee and a bounded scheduled cleanup before promising one. Private receipt IDs/hash/time and moderated Gazette/review records remain until a separately approved retention/deletion policy; the receipt does not duplicate the report text.

The handler's eight-second application budget covers request and response bodies and aborts its fetch; this is separate from Netlify's platform execution limit. Client budget is ten seconds. A database operation may commit after a network timeout; idempotent receipt recovery is the protection, not an assertion that an aborted fetch rolled back a database transaction. SQL has lock/statement timeout settings, but production timeout behavior still needs deployment proof. No 48-hour review SLA, first-reporter ranking, AfroPoints award or automatic publication is implemented or promised.
