# AfroStatus Product Health Contract

`/status/` is AfroTools' public-safe summary of product availability, data coverage,
freshness, and production release identity. It is deliberately a small aggregation
layer, not a separate observability system.

## Source ownership

The committed fallback snapshot is generated by `scripts/build-product-health.js`
from existing source ledgers. Product owners should update those ledgers through
their normal workflows instead of editing `status/product-health.json` or the
embedded snapshot in `status/index.html` by hand.

- Fuel: `data/fuel/latest.json`
- Mobile Money: `data/fintech/mobile-money-tariffs.json`
- Electricity: `data/energy/electricity-tariffs.json`
- FX: `data/forex/latest.json`
- PAYE/tax: `data/source-registry.json`
- Scholarships: `data/scholarships/official-sources.json`
- Transport: `data/transport/source-status.json`
- AfroStream fallback: `data/afrostream/creators-fallback.json`
- Platform release verification: `data/_meta.json`

Run `npm run product-health:build` after an owning source changes. CI and release
builds run `npm run product-health:check` to reject drift.

## Truth rules

- A timestamp is required before evidence can be operational.
- Evidence beyond its expected cadence is stale even when a source declares itself
  operational.
- Unknown and unchecked systems remain unknown.
- Partial coverage is distinct from freshness.
- A successful response with zero usable records is not operational.
- Public reasons must not contain credentials, internal hostnames, private logs,
  admin details, or security-sensitive infrastructure information.

The static snapshot renders before any network request. The browser may overlay
newer public evidence from `/api/data-freshness` and `/api/afrostream/health`, but
failed live checks cannot erase the last safe snapshot or upgrade an unknown state.

## Release visibility

`changelog/releases.json` is the allowlisted public annotation ledger. Entries must
refer to merged repository history and describe user-visible production candidates;
raw commit messages are never exposed automatically.

`scripts/build-dist.js` writes `dist/status/release.json` from Netlify's public build
context. It contains only the production flag, a hexadecimal commit SHA, and an ISO
build time. A merge annotation is not described as production until this receipt
comes from a production-context build.

## Validation

Run the focused contract with:

```text
npm run product-health:check
npm run test:product-health-status
npm run test:product-health-status:browser
```

Because status and release metadata affect the publish surface, release candidates
also require `npm run security:scan`, `npm run build:deploy`, and
`npm run audit:dist`.

## Recommended automation

The publisher should add a reviewed public release annotation and publish the safe
release receipt only after a successful production deployment. A scheduled health
job should evaluate reachability, freshness, and non-empty usable content as separate
signals, retain the last-known-good snapshot, and alert on state transitions without
publishing raw provider errors.
