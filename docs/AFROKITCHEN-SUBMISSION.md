# AfroKitchen private recipe submissions

The contribution form sends only after the contributor checks the private editorial consent box and presses **Send recipe for review**. Optional name/email are included in that disclosed send. Typing does not send or save anything remotely. The draft remains in the current page only; copy it before closing or retrying an unconfirmed request. Photo links also require the separate rights checkbox. Links remain passive editorial text; ingestion never fetches them.

`AfroKitchenEngine.submitRecipe` posts JSON to the existing same-origin `/.netlify/functions/afrokitchen-community` with `action: "submit-recipe"`. It uses no browser database client, credentials or retries. Server dispatch occurs before the existing published-parent UUID requirement, while review and cooksnap retain their published-parent checks.

The new action accepts only the named recipe/context/contact fields, typed consent/photo permission, and empty `website` honeypot. It checks a first-party AfroTools production/preview or loopback Origin and JSON content type. There is a 64KiB UTF-8 submission cap. Required fields are name, listed country, ingredients and steps. Limits in characters: name160, description500, ingredients12000, steps18000, story8000, author80, email254, region160, contributor type80, occasion160, approximate time160, serving suggestion500, photo links2000, variations2000. Combined story plus server-composed editorial context is at most12000. Unicode and multiline recipe text are retained; control characters are rejected. Downstream editorial rendering must escape stored text.

The shared limiter permits five validated attempts per IP per day **per warm function instance**. It prefers Netlify's client connection IP, uses existing fallback headers and keeps an unknown-IP bucket. It is bounded memory, resets on cold starts and is not a global quota or identity check. Origin, honeypot and this quota do not establish contributor ownership or authentication.

Server configuration must point to `https://zpclagtgczsygrgztlts.supabase.co` and supply the existing server-only service key. Ingestion inserts one record into the fixed private `recipe_submissions` table with forced `status: "pending"`; it has no public readback, publication, row update, role/table override, notification or email side effect. No RLS/grant change is part of this repair. Schema/default/service privilege qualification belongs to the release owner before any live use.

Success requires PostgREST's successful HTTP201 return=minimal insert, then exact HTTP201 `{ "success": true, "status": "pending" }` at the client. Generic200, partial acknowledgements, errors and malformed responses never hide the form. Provider diagnostics and PII are not echoed or logged. Server header wait is bounded at8s; the minimal insert response needs no body parsing. Client header/JSON wait is bounded at12s. Neither retries automatically. Timeout/failure may leave persistence unconfirmed, so a contributor's manual retry can create another submission; no exactly-once claim is made.

The form retains its disabled inflight button, `aria-busy`, live status, native validation and snapshot/revision comparison. A failed/unconfirmed send keeps the draft. A confirmed older snapshot keeps newer edits visible. Only an unchanged confirmed pending snapshot shows the saved success state. Server field errors use an allowlisted control mapping, `aria-invalid`, linked status and focus; no provider HTML is rendered.

Focused checks: `node --test tests/afrokitchen-submission.test.js tests/afrokitchen-publication-boundary.test.js`; the maintained `tests/e2e/afrokitchen-submission-recovery.spec.js` covers the actual form/engine with synthetic same-origin responses and blocked external requests. Browser results are a separate local mocked transport layer; they cannot establish deployed function behavior or real database persistence. Full build/dist/security checks and live persistence remain release gates.
